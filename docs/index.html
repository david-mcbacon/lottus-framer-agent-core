@lottus-agent/framer-core · MIT · v0.1.0

One Framer agent brain,
every place Lottus runs.

Framer Agent Core is the shared, open-source rulebook that decides how an AI agent is allowed to touch your Framer project — what it may change, what proof it must collect, when it must stop and ask you, and when it is genuinely done.

MIT licensed Certified against Pi 0.80.6 Node 20+, ESM Runs in Lottus Desktop & Lottus Cloud
01 — What this is

A rulebook, not an app

When you ask Lottus to “make the hero section tighter on mobile”, something has to translate that into actual, safe operations against your real Framer project. That something is the agent runtime: the set of tools the AI is allowed to call, the order it must call them in, the checks it must pass, and the shape of the answer it gives back.

Framer Agent Core is exactly that runtime, packaged on its own and published openly. It has no windows, no buttons and no login screen. Lottus Desktop and Lottus Cloud each wrap it in their own interface — but the behaviour underneath is byte-for-byte the same.

For designers

Predictable behaviour

The agent follows the same safety rules whether you work on your laptop or from the Framer plugin.

For designers

Honest results

It cannot claim “done, all clean” unless Framer itself confirmed there were no errors.

For engineers

One place to fix things

Every tool invariant lives once. A correctness fix ships to both hosts through one version bump.

🍊 In one sentence

Core owns what agent work means; the hosts own where it runs and how it looks.

02 — The problem it solves

The same rules were written twice

Lottus Desktop and Lottus Cloud each grew their own copy of the Framer agent behaviour. Two copies means two sets of bugs, two safety reviews for every improvement, and — the real problem — two different answers to the same request. The copies had already started to drift apart.

What that buys you

  • Consistency. Moving from desktop to hosted doesn’t change the quality or the safety of the result.
  • Trust. The intelligence is public. You can read exactly what the agent is permitted to do to your project.
  • Speed of improvement. A single safety fix reaches everyone rather than being ported by hand.
03 — Precondition

Core needs a live Framer session

This is the single most important thing to understand. Framer Agent Core starts after the door is already open. It does not log you in, does not pick your project, and does not keep a connection alive. It assumes a host has already connected to a running, authenticated Framer project and can execute operations against it right now.

⚠️ If the session drops, the work stops

Core has no way to reconnect you — it only knows how to ask the host to run an operation. If your Framer project closes mid-run, the agent’s next operation fails and the run ends with unfinished work rather than a false “all done”.

Engineer note — why this boundary is deliberate engineering

Connection establishment is where the security models genuinely diverge: desktop discovers a local Framer CLI and runs a local relay under the user’s own identity; cloud runs inside a Tenant Sandbox with privileged process identity, environment allowlisting and process-group termination. Pulling that into a shared package would force tenant isolation logic into a public repo and produce host conditionals throughout the core.

By starting the scope after connection, the only shared surface is “execute this operation and give me the output”, which is a genuine seam — two real adapters already implement it.

04 — Architecture

Three layers, two plugs

Core sits in the middle. Above it, a host renders the conversation. Below it, a host executes real operations. The two “plugs” between them are called adapters — small pieces of code each host supplies so Core never has to know whether it’s inside an Electron app or a cloud sandbox.

05 — Capabilities

What the agent can actually do

The agent isn’t allowed to improvise. It has a fixed, small set of tools, and Core defines each one’s name, inputs, ordering and the exact shape of its result. Anything outside this list simply isn’t possible.

ToolIn plain termsGuardrail
framer_docsLook up how a specific Framer API works.Symbol must match exactly — no guessing at names.
framer_execRead or inspect things in your project.Raw canvas-apply and raw code-file lifecycle calls are prohibited here.
framer_apply_changesMake a focused change on the canvas.Output is normalized into evidence: clean, issues, or incomplete.
framer_read_code_fileRead a code component before touching it.Creates a snapshot + token used to detect later conflicts.
framer_create_code_fileAdd a new code component.Refuses to overwrite an existing file.
framer_update_code_fileEdit an existing code component.Only succeeds if the remote file still matches the snapshot.
framer_check_code_fileVerify exports and diagnostics after a change.Feeds the completion gate.
ask_userAsk you one design decision and stop.2–4 visible options, max one recommendation.
finish_framer_workDeclare the work finished.Blocked unless evidence for the latest change is complete.
Why so few?

A small, strictly-typed tool set is what makes the behaviour reviewable. Every rule you care about — “read before write”, “verify after write”, “don’t claim success without proof” — is expressible as a constraint between these nine tools.

06 — Design Questions

When it doesn’t know, it asks you — properly

Sometimes a request has a genuine fork in it. Should the nav collapse into a hamburger or scroll horizontally? Rather than guessing — or burying the question in a wall of text — Core makes the agent raise a Design Question: one clear question, two to four visible outcomes you can choose between, described in design language rather than code.

1
The agent hits a real fork Not “which prop should I use” — something you would actually see on the page.
2
It asks exactly one question Two to four options, each a visible outcome. At most one is marked as a recommendation.
3
The run ends there No spinner left hanging, no background process waiting for you. The agent stops cleanly.
4
You answer whenever you like Ten seconds or two days later. Your answer starts a fresh run that continues the work.
🍊 Why stopping is a feature

An agent that keeps a process alive while waiting for you is fragile — it dies with a network blip and it can’t be scheduled or resumed. Ending the run and resuming from your persisted answer means a question can safely sit unanswered overnight.

Engineer note — the structured contract engineering

ask_user returns terminating tool details discriminated by lottus_design_question. Hosts must never parse assistant prose to detect a question. Core validates option uniqueness, the 2–4 option bound, and the at-most-one-recommendation rule; it does not define presentation or persistence.

Desktop historically allowed free-prose questions and is being standardized onto this same contract, which is what makes future workflow runners (pause → persist → resume) possible without a second agent implementation.

07 — Code files

Never overwrite work you didn’t see

Code components are the easiest thing for an agent to damage. Core enforces a strict cycle: read, snapshot, edit, verify — and it refuses the edit if anything changed underneath in the meantime.

What this prevents, in real life

  • A teammate edits the same component in Framer while the agent is thinking — their work survives.
  • The agent writes a component that no longer exports what Framer expects — caught before you’re told it’s done.
  • The agent “fixes” a file it never read — not possible; the update needs a token from a read.
Engineer note — snapshots, tokens and limits engineering

Reads and checks write a model-readable snapshot through the scratch adapter and mint an opaque run-local token. Tokens are scoped to the Pi session and cannot be replayed across sessions. Core owns filename validation, source-size limits, generated Framer operation scripts, export normalization and diagnostics parsing; the adapter owns path authorization and filesystem security.

A conflict is a non-mutating outcome: the remote file is untouched and the agent is instructed to read and reapply. Creation refuses to overwrite. Post-mutation verification must be complete before the mutation can be reported clean.

08 — Evidence & completion

“Done” has to be earned

Every change the agent makes produces raw output from Framer. Core turns that output into evidence with one of three statuses — and it deliberately refuses to be optimistic when it can’t tell.

Clean

Framer confirmed it

The change applied and diagnostics came back with nothing to report.

Issues

Something needs attention

Errors or warnings were reported. They must appear in the summary as unresolved issues.

Incomplete

Can’t tell

Output was missing or unrecognisable. This is never upgraded to success.

The finish_framer_work tool checks all of this before it will let the run end. If your most recent change has incomplete evidence, completion is rejected and the agent has to go verify. If evidence reports issues, the summary must list them — it can’t quietly drop them.

What you get back at the end

  • A summary of what was done, in plain language.
  • Visible changes — what actually looks different in your project.
  • Review status — derived from the evidence, not from the agent’s mood.
  • Unresolved issues — present exactly when evidence says issues remain.
  • Publication state — whether the project was published.
Engineer note — Framer Run State & isolation engineering

A session-local Framer Run State owns canvas and code-file mutation versions, verification versions, evidence status, diagnostics, publication state, derived review status and completion-blocking reasons. It is created per extension assembly, so parallel desktop sessions and separate Tenant Operations cannot bleed state into one another — this is covered by explicit isolation tests.

Completion returns terminating details discriminated by lottus_framer_completion. Both the question and completion discriminators are treated as public compatibility contracts; hosts render them and must not depend on presentation text.

09 — Guidance

Progressive disclosure: the agent reads what it needs

Framer is enormous. Pouring every API document into the agent’s head at once makes it slower, more expensive and — counter-intuitively — less accurate, because the important rules get diluted.

So Core compiles Framer material into layers. The agent always carries a small set of operating rules. Everything else is an index it can walk into on demand: a short routing map that points at detailed references, which it opens only when the task actually calls for them.

Why designers should care

  • Sharper answers. The rules that keep your project safe aren’t drowned in API trivia.
  • Cheaper, faster runs. Less text loaded per turn.
  • Nothing goes missing. If Framer changes its docs format, Core keeps the complete original as a fallback and flags it — rather than silently dropping instructions.
Engineer note — determinism and provenance engineering

compileFramerGuidance is pure: the same inputs always yield the same routed references, Project Inventory shards, fallback files, coverage/provenance records, warnings and content hash. A changed Workspace Hash therefore always has an explainable source.

Hosts layer explicit, attributed additions — Desktop adds local Git-history policy, Cloud adds Tenant Sandbox operating policy — without forking the shared base document.

Licensing: Core ships no Framer-derived task guidance. Only Lottus-authored base instructions are published under MIT; Framer-derived material is discovered at runtime from the user’s own installed Framer tooling or supplied by the host. A redistribution manifest plus packed-artifact tests fail the build if an unaudited Markdown asset enters the tarball.

10 — Using it

Install & assemble

If you’re a designer using Lottus Desktop or the Framer plugin, Core is already inside — there’s nothing to install. This section is for developers embedding the runtime in their own host. 

pnpm add --save-exact @lottus-agent/framer-core@0.1.0

Then assemble the extension with your two adapters:

import {
  createFramerAgentCoreExtension,
  type FramerExecutionAdapter,
  type FramerScratchFileAdapter,
} from "@lottus-agent/framer-core";

const extension = createFramerAgentCoreExtension({
  executionAdapter: hostFramerAdapter,   // talks to the Live Framer Session
  scratchAdapter: hostScratchAdapter,    // reads/writes agent scratch files
});

Supplying only the execution adapter registers framer_docs, framer_exec, framer_apply_changes and finish_framer_work. Adding the scratch adapter also registers the four code-file tools. ask_user is always available.

Engineer note — versioning, prereleases and rollback engineering
  • Exact versions only in production hosts. link: and file: references are development-only and must never be committed to release configuration.
  • Prereleases ship under the rc tag; install the immutable version, not the moving tag, and verify against real artifacts (Docker image, packaged Electron build).
  • Packed-artifact testing installs the tarball into a clean fixture, imports every documented export and confirms Pi resolves to the host copy.
  • Rollback = reinstall the last verified exact version and regenerate the lockfile. Versions are immutable; never unpublish or replace an artifact.
11 — Adapters

The two plugs, in detail

Adapter 1

Framer execution

“Run this documentation lookup / this JavaScript against the connected project, and hand me the output.” Covers cancellation, timeouts, raw output, a truncated visible output, and optional structured-result extraction.

Adapter 2

Scratch files

“Read the source the agent authored, and write a snapshot the model can read.” Core owns the snapshot workflow and size rules; the host owns path authorization and filesystem security.

Both plugs already have two real implementations — local (Electron) and Tenant Sandbox — which is why they are genuine seams rather than speculative abstraction. Core also ships fake adapters in its testing export, so the whole runtime can be exercised without a live Framer project at all.

Conformance kit

One shared conformance suite runs against both host assemblies. Each host proves its adapters satisfy the interface; hosts don’t re-test agent semantics, which stay in Core’s own suite.

12 — Boundaries

What Core deliberately does not do

Knowing what’s not in the box is as useful as knowing what is.

Connections & credentials

No project authorization, relay lifecycle, session creation or reconnection, credential storage or health checks.

Interface

No Framer plugin UI, no desktop React presentation, no terminal rendering, no shared UI toolkit.

Tenant security

Sandbox identity, protected paths, process isolation and multi-tenant policy stay private to Lottus Cloud.

Persistence & scheduling

No workflow engine, cron, webhooks, queues, retries, approvals or history storage — yet.

Standalone install

v0.1.0 is an embedded library, not an independently installable terminal package. A thin wrapper can come later.

Other runtimes

Node-only. No browser, mobile, or non-Pi agent runtime support, and no Pi version range beyond 0.80.6.
